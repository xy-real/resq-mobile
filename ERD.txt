                        AUTHENTICATION & SECURITY
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

SUPABASE AUTH INTEGRATION:
───────────────────────────────────────────────────────────────────────────
• auth.users table managed by Supabase (not in this schema)
• Passwords securely hashed and stored by Supabase Auth
• user_id in STUDENTS and ADMINS links to auth.users(id)
• Two authentication methods supported:
  1. Google OAuth (automatic email verification)
  2. Email/Password (requires email verification via Gmail)

REGISTRATION FLOW:
───────────────────────────────────────────────────────────────────────────
For Students:
  1. User signs up via Google OAuth or email/password
  2. Account created in auth.users (Supabase managed)
  3. Email verification (for email/password signups)
  4. User completes registration form
  5. Record inserted into STUDENTS table with:
     - user_id = auth.uid() (links to authenticated user)
     - student_id = university ID (from form)
     - email = from auth user
     - name = from form

For Admins:
  1. Same authentication flow as students
  2. Record inserted into ADMINS table
  3. All admins have equal privileges

SECURITY PRINCIPLES:
───────────────────────────────────────────────────────────────────────────
• NEVER store passwords in application tables
• RLS policies enforce data isolation between users
• auth.uid() used to match authenticated user to table records
• Students can only access their own data
• Admins can access all data for oversight
• SMS gateway uses service role key (bypasses RLS)

PRIVACY NOTES:
───────────────────────────────────────────────────────────────────────────
• Location Data: Students see only their own GPS coordinates
• Status Logs: Complete audit trail, students see only their history
• Disaster Mode: Read-only for students, write access for admins
• Admin Privileges: All admins have equal access (no role hierarchy)

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. update_student_status(student_id, status, source, lat, lng, validation)
   - Updates student status and creates log entry
   - Used by mobile app and SMS gateway

2. auto_triage_students()
   - Marks inactive students as UNKNOWN after 6 hours
   - Called by cron job when disaster mode is active

3. get_dashboard_metrics()
   - Returns real-time counts of students by status
   - Used by admin dashboard

4. toggle_disaster_mode(activate)
   - Activates or deactivates disaster mode
   - Only callable by admins (protected by RLS)

5. is_location_valid(old_lat, old_lng, new_lat, new_lng, threshold)
   - Validates location updates (100m movement threshold)
   - Used to detect significant location changes
